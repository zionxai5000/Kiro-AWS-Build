## Section 2: Apple App Store Connect Metadata API

### Key Concept: Bundle ID ≠ App Entity

- **Bundle ID** (Apple Developer Portal): Registered via `POST /v1/bundleIds`. We already do this in Step 4 of the iOS credential bootstrap. Resource ID example: `US85GDKZ7V`.
- **App Entity** (App Store Connect): A separate resource representing the app listing. Created via `POST /v1/apps`. Has its own numeric Apple ID (the `ascAppId` that EAS Submit needs).

These are SEPARATE resources with separate IDs. Having a bundle ID does NOT mean you have an App Store Connect app. The app entity must be created separately.

### Creating an App in ASC

Endpoint: `POST /v1/apps`

Required fields:
- `bundleId` — relationship to the registered bundle ID resource
- `name` — display name (2-30 chars, must be unique on the App Store)
- `primaryLocale` — e.g., "en-US"
- `sku` — internal identifier (not visible to users, must be unique per account)

Authentication: Same ASC JWT we already use (ES256, same key).

### Setting App Metadata

After creating the app, metadata is set via localization resources:

| Endpoint | Fields |
|----------|--------|
| `PATCH /v1/appInfoLocalizations/{id}` | name, subtitle, privacyPolicyUrl |
| `PATCH /v1/appStoreVersionLocalizations/{id}` | description, keywords, whatsNew, supportUrl, marketingUrl |
| `PATCH /v1/appInfos/{id}/relationships/primaryCategory` | category |

### Draft State

Apps can exist in ASC without being submitted for review. The listing stays in "Prepare for Submission" state until explicitly submitted. This means we can:
1. Create the app entity
2. Set all metadata
3. Upload screenshots
4. Leave it in draft — operator submits when ready

This aligns with Hook 9's design: "does NOT auto-submit."

### Required Fields for Submission (minimum viable)

Per Apple's reference, these are required before submission:
- App name (2-30 chars)
- Subtitle (optional but recommended, max 30 chars)
- Description (min 10 chars, max 4000 chars)
- Keywords (max 100 chars, comma-separated)
- Support URL
- Privacy Policy URL
- Primary category
- At least one screenshot set (see Section 6)
- App icon (already generated by Hook 7)
- Build (already produced by Hook 6)

## Section 3: EAS Submit (iOS)

### Command

```
eas submit --platform ios --non-interactive
```

### Configuration (eas.json)

```json
{
  "submit": {
    "production": {
      "ios": {
        "ascAppId": "1234567890"
      }
    }
  }
}
```

### Key Requirements

1. **`ascAppId` is required** — this is the App Store Connect app's Apple ID (numeric). It's NOT the bundle ID. It's found in ASC under App Information → General Information → Apple ID.
2. **ASC API Key must be configured** — either via `eas credentials` or via `ascApiKeyPath`, `ascApiKeyIssuerId`, `ascApiKeyId` fields in eas.json. We already have these credentials from the bootstrap.
3. **A production build must exist** — we have this from Hook 6.
4. **The app must exist in ASC** — we need to create it first (Section 2).

### What EAS Submit Does

- Uploads the .ipa to Apple via Transporter (or equivalent)
- The build lands in TestFlight first
- From TestFlight, it can be promoted to App Store review

### What EAS Submit Does NOT Do

- Does NOT create the app in ASC (must exist already)
- Does NOT set metadata (name, description, keywords)
- Does NOT upload screenshots
- Does NOT submit for App Store review (only uploads to TestFlight)

### Implication for Our Pipeline

Hook 8 (store-listing-writer) must:
1. Create the app in ASC if it doesn't exist
2. Set all metadata via ASC API
3. Upload screenshots via ASC API

Hook 9 (submission-prep) must:
1. Verify all metadata is set
2. Run `eas submit --platform ios` to upload build to TestFlight
3. Optionally: submit for App Store review via ASC API (`POST /v1/appStoreVersionSubmissions`)

## Section 4: EAS Submit (Android)

### Command

```
eas submit --platform android --non-interactive
```

### Configuration (eas.json)

```json
{
  "submit": {
    "production": {
      "android": {
        "track": "internal",
        "serviceAccountKeyPath": "./google-service-account.json"
      }
    }
  }
}
```

### Key Requirements

1. **Google Service Account Key** — JSON file with Play Console API access. Must be uploaded to EAS or provided via path.
2. **App must exist in Google Play Console** — created manually via web UI.
3. **First submission must be manual** — Google Play Store API limitation. The very first .aab upload must go through the Play Console web UI. After that, EAS Submit can handle subsequent uploads.
4. **Track selection** — `internal` (fastest, no review), `alpha`, `beta`, `production` (requires review).

### What EAS Submit Does (Android)

- Uploads the .aab to Google Play via the Play Developer API
- Places it on the specified track
- For `internal` track: available immediately to internal testers
- For `production` track: enters Google's review queue

### Critical Limitation: First Release

The first release of an Android app CANNOT be automated. Google requires:
1. Manual creation of the app in Play Console
2. Manual upload of the first .aab
3. Manual completion of the store listing (content rating, privacy policy, etc.)
4. Manual submission for review

After the first release is approved, subsequent updates can be automated via EAS Submit.

### Implication for Our Pipeline

For the MVP (single-tenant, `dev.zionxai.workouttracker`):
- The first Android submission is a manual step (operator does it once)
- After that, Hook 9 can automate updates via `eas submit --platform android`

For multi-tenant (future):
- Each new app requires a manual first submission
- This is a hard constraint from Google — no API workaround exists
- Consider: generate the .aab + store listing, then provide instructions for the manual first upload

## Section 6: Screenshot Strategy

### Apple Requirements (2026)

Per current Apple guidelines:
- **Minimum**: One screenshot set for 6.9" OR 6.5" display (required for all new submissions)
- **Maximum**: 10 screenshots per device class per localization
- **Auto-propagation**: If you upload 6.9" screenshots, Apple automatically scales them for smaller devices
- **Required sizes**:
  - iPhone 6.9" (iPhone 16 Pro Max): 1320×2868 px
  - iPhone 6.7" (iPhone 16 Plus / 15 Pro Max): 1290×2796 px
  - iPhone 6.5" (iPhone 11 Pro Max): 1242×2688 px (legacy, still accepted)
  - iPad 12.9" (if supporting iPad): 2048×2732 px
- **Format**: PNG or JPEG, no alpha channel, no device frames in the image itself
- **Content**: Must be actual app screenshots (not marketing material with people holding devices)

### Google Play Requirements

- **Minimum**: 2 screenshots
- **Maximum**: 8 screenshots
- **Size**: Min 320px, max 3840px on any side. Aspect ratio max 2:1.
- **Recommended**: 1080×1920 px (portrait) or 1920×1080 px (landscape)
- **Format**: PNG or JPEG

### Generation Strategy Options

| Option | Approach | Pros | Cons |
|--------|----------|------|------|
| **A** | Simulator capture | Most authentic, real app UI | Requires running the app (Expo Go or dev build), complex automation (Detox/Maestro), slow, fragile |
| **B** | React Native rendering + device frames | Renders components to images, adds device bezels | Requires a rendering server, complex setup, but produces realistic results |
| **C** | AI image generation (OpenAI/DALL-E) | Fast, cheap ($0.04/image), already have the client | Not actual app screenshots — Apple may reject if they look too "generated". Less authentic. |
| **D** | Placeholder screenshots for MVP | Generic "Coming Soon" or solid-color placeholders | Fastest to implement, but won't pass App Store review. Only useful for internal testing. |

### Recommended Approach (for discussion)

**Option C (AI generation) for MVP, Option A/B for production quality.**

Rationale: We already have the OpenAI images client from Hook 7. We can generate promotional-style screenshots that show the app concept. For the first submission, this gets us through the door. For production quality, we'd need Option A or B — but that's significantly more infrastructure.

**Open question**: Apple's guidelines say screenshots must be "actual app screenshots." AI-generated images that look like app screens may or may not pass review. This is a risk.

## Section 7: Open Questions for Design Phase

1. **Should Hook 9 auto-submit or stop at the checklist?**
   - Current stub says "does NOT auto-submit" — requires explicit confirmation
   - But the confirmation could be a simple API call (`POST /app-dev/submit/confirm`)
   - Decision: keep the two-step pattern (prep → confirm) or make it one-step?

2. **How do we handle the first-Android-release manual Play Console step?**
   - Option A: Pipeline generates everything, provides step-by-step instructions for manual upload
   - Option B: Pipeline detects "first release" and halts with clear error + instructions
   - Option C: Defer Android submission entirely until after first manual release is done

3. **Which screenshot strategy do we pick?**
   - For MVP: Option C (AI) or Option D (placeholder)?
   - For production: Option A (simulator) or Option B (render)?
   - Timeline impact: Option C adds ~1 day, Option A adds ~3-5 days

4. **Multi-tenant: how does Phase 8 handle multiple Apple teams / Google Play accounts?**
   - Currently `apple-credentials-config.ts` is single-tenant
   - Phase 8 needs per-project ASC app IDs, per-project Google Play apps
   - Should we solve this now or defer to Phase 9?

5. **ASC App creation: who owns the app entity?**
   - Our pipeline creates the app in ASC under the `zionxai` account
   - For multi-tenant, each user would need their own Apple Developer account
   - Single-tenant MVP: all apps under `zionxai` account (fine for now)

6. **What's the `ascAppId` lifecycle?**
   - Created when we `POST /v1/apps` — Apple returns the numeric ID
   - Must be stored somewhere (workspace metadata? database?)
   - Hook 9 needs it for `eas submit`
   - Proposal: store in workspace's `eas.json` under `submit.production.ios.ascAppId`

7. **Privacy Policy URL requirement**
   - Apple requires a privacy policy URL for all apps
   - Options: generate a generic one, use a template hosted on our domain, or require user input
   - This blocks submission if not provided
